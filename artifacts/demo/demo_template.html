My own RISC‑V core runs speculative decoding on an FPGA

A small draft model guesses the next tokens, and a custom LLM unit checks every guess in one pass over the weights. The output is identical and 1.16× faster, measured on an AMD Kria KV260.

Watch the replay Read the code on GitHub

How it works

Generating text one token at a time is limited by memory: every token reads all the weights once and does about one multiply per byte. Speculative decoding reuses each weight read for several tokens, so the hardware’s job is to make checking three tokens cost about as much as checking one.

  1. The draft guesses

    A 0.66M-parameter draft model, distilled from the target, proposes the next two tokens. It costs about 18% of a target pass.

  2. The target checks them together

    The 5.2M-parameter target runs one pass with three lanes. Each weight word streamed from DDR is multiplied against all three lanes in the same cycle.

  3. Keep what agrees

    Guesses that match the target’s own choice are kept, the first mismatch is replaced by the target’s token, and the next round starts. The text is exactly what plain decoding would write.

How I checked it

    

      
Bit-exact everywhere
The PyTorch integer model, the C reference and the core produce identical numbers. All 50 board prompts match the reference token for token.

      
Board equals simulation
A full 100,556,084-cycle model run took the same number of cycles on the KV260 as in RTL simulation.

      
The LLM unit
UVM testbench with a scoreboard and coverage, SVA properties, and mutation testing: a seeded bug triggered 42 scoreboard errors and 7 assertion failures.

      
The core
A 586-case RV32IM ISA test and a constrained-random test against a Python instruction-set simulator, which caught all 3 bugs seeded into the pipeline.

    

  


  

    
Limitations and next steps

    

      
Limitations
The models are tiny (5.2M and 0.66M parameters, 2,048-token vocabulary), so the code they write is rough. The speedup is modest: each extra verify lane still costs about a third of a pass because attention, norms and the readout run in software on the core, and 5 of 50 prompts are slower than plain decoding. The board runs at 50 MHz, so in absolute speed the core is slower than the board’s own Arm cores; the comparison that matters is plain against speculative on the same core. Decoding is greedy only, tested on contexts up to 48 tokens.

      
Next steps
Move attention, norms and the readout into hardware so that extra lanes cost almost nothing. Run larger open model pairs at int8 or int4, with a wider engine sized to the board’s memory bandwidth. Raise the clock, and stream tokens live from the board.
